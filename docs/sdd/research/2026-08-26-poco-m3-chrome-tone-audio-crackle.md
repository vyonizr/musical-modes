# POCO M3 Chrome audio crackle: source-checked possibilities

**Status:** research only. This note does not diagnose the reported sporadic crackle. It records what the checked source supports and the observations that would separate the possibilities on the affected phone.

## Verified app and Tone.js facts

- This checkout uses Tone.js **15.1.22** ([package lock-in](../../../package.json), [installed package metadata](../../../node_modules/tone/package.json)). Its shared path is **Sampler or PolySynth → Reverb({ decay: 1.5, wet: 0.3 }) → Volume → Limiter(-2) → destination** ([app graph](../../../src/utils/chords.ts#L212-L232)). Therefore a fault in that output chain is common to every app input path; that fact alone does not identify the fault.
- The current checkout schedules each chord tone separately at `Tone.now() + random(0, 0.012)`, at velocity `0.64…0.76` ([app timing constants](../../../src/utils/chords.ts#L59-L78), [attack loop](../../../src/utils/chords.ts#L400-L418)). This is **0–12 ms**, rather than the 0–30 ms stated in the incident context.
- In Tone 15.1.22, the lazily created global context is a `new Context()` ([source](https://github.com/Tonejs/Tone.js/blob/15.1.22/Tone/core/Global.ts#L24-L35)); its defaults set `lookAhead` to 0.1 s and `Tone.now()` is raw `AudioContext.currentTime + lookAhead` ([source](https://github.com/Tonejs/Tone.js/blob/15.1.22/Tone/core/context/Context.ts#L146-L152), [source](https://github.com/Tonejs/Tone.js/blob/15.1.22/Tone/core/context/Context.ts#L464-L465)). In the default configuration, those 0–12 ms offsets are therefore scheduled about 100–112 ms ahead of raw context time.
- `Tone.Sampler` chooses the nearest loaded sample for a requested pitch, creates a `ToneBufferSource` for every attacked note, and tracks active sources ([Sampler source](https://github.com/Tonejs/Tone.js/blob/15.1.22/Tone/instrument/Sampler.ts#L173-L230)). `ToneBufferSource` wraps a native `AudioBufferSourceNode` ([source](https://github.com/Tonejs/Tone.js/blob/15.1.22/Tone/source/buffer/ToneBufferSource.ts#L35-L43)). Repeated overlapping chord attacks are thus a concrete source-count/load variable to measure.
- Tone's `Reverb` creates a decaying-noise impulse response in an `OfflineContext`, installs it in a native `ConvolverNode`, and documents that its asynchronous `ready` promise must resolve before it makes sound ([source](https://github.com/Tonejs/Tone.js/blob/15.1.22/Tone/effect/Reverb.ts#L14-L18), [source](https://github.com/Tonejs/Tone.js/blob/15.1.22/Tone/effect/Reverb.ts#L91-L125)). This app creates that shared output while preloading samples after first paint ([call site](../../../src/App.tsx#L57-L62), [construction](../../../src/utils/chords.ts#L245-L259)); it does not wait for `reverb.ready` ([construction](../../../src/utils/chords.ts#L212-L216)). That makes **startup-only** behavior a distinct probe, not evidence for an intermittent steady-state cause.
- Tone's `Limiter(-2)` is a `DynamicsCompressorNode` wrapper with threshold -2 dB, ratio 20, 3 ms attack, and 10 ms release; its `reduction` value reports applied gain reduction ([source](https://github.com/Tonejs/Tone.js/blob/15.1.22/Tone/component/dynamics/Limiter.ts#L12-L17), [source](https://github.com/Tonejs/Tone.js/blob/15.1.22/Tone/component/dynamics/Limiter.ts#L45-L74)). It limits loudness, but source does not establish that it prevents every possible output-stage distortion.

## Render quanta, main thread, and AudioWorklet

Web Audio renders a graph in fixed blocks. The default render quantum is 128 frames, while the system audio callback asks for a buffer that must be computed before the next callback ([Web Audio rendering loop](https://webaudio.github.io/web-audio-api/#rendering-loop)). The specification defines an **audio buffer underrun** as renderer load greater than 1.0: the system did not render audio fast enough for real time ([same source](https://webaudio.github.io/web-audio-api/#rendering-loop)).
The Web Audio working group's Android render-size explainer gives a concrete risk model: a 128-frame Web Audio quantum on a device whose native callback is 192 frames alternates between one and two graph renders, so every other 2.666 ms interval at 48 kHz must complete twice the average work. It explicitly says this raises peak CPU demand and limits graph complexity on Android ([explainer](https://github.com/WebAudio/web-audio-api/blob/main/explainer/user-selectable-render-size.md#issues)). The same explainer notes that `ConvolverNode` implementations commonly use FFTs and need buffering considerations ([implementation note](https://github.com/WebAudio/web-audio-api/blob/main/explainer/user-selectable-render-size.md#convolvernode-implementation)). This app does use a `ConvolverNode` through Tone `Reverb`; the source does **not** establish the POCO M3 callback size or prove this is the reported cause.

AudioWorklet puts user-supplied processor JavaScript on the audio rendering thread. Chrome contrasts that with main-thread `ScriptProcessorNode` handlers, whose UI-thread work can cause audio glitches ([Chrome AudioWorklet documentation](https://developer.chrome.com/blog/audio-worklet)). The checked Sampler, Reverb, and Limiter implementations above use native Web Audio sources/effects; the app's attacks originate from ordinary React/DOM event handlers, for example the chord-cell `onPointerDown` ([app call site](../../../src/components/TableContent.tsx#L29-L40), [Tone sources above](#verified-app-and-tonejs-facts)). A blocked main thread can therefore delay a new attack being submitted, while an event already scheduled in the look-ahead window is rendered by the audio graph. This distinction does **not** prove that a main-thread stall or a render underrun occurred.

Chrome's WebAudio panel exposes the context state, system callback buffer size, callback-interval variance, and **Render Capacity** (renderer work as a percentage of its render budget) ([Chrome DevTools reference](https://developer.chrome.com/docs/devtools/webaudio)). Chrome supports inspecting the live Android tab from desktop DevTools over USB ([Chrome Android remote-debugging guide](https://developer.chrome.com/docs/devtools/remote-debugging)). These are feasible measurements on the actual POCO M3.

## Crackle classes to keep separate

| Class | Source-backed definition / graph relevance | Observation that distinguishes it on the POCO M3 |
| --- | --- | --- |
| **Real-time render underrun** | The Web Audio definition is renderer load > 1.0, meaning it missed real-time production of audio ([spec](https://webaudio.github.io/web-audio-api/#rendering-loop)). It is a timing/deadline failure, independent of whether the musical signal is loud. | Remote-inspect the live phone. Mark each audible event and record WebAudio **Render Capacity**, callback interval, callback buffer size, sample rate, and context state. A crackle that coincides with capacity reaching/exceeding the available budget or an interval disturbance supports this class. Reproduce at the same app volume with progressively more overlapping attacks. No such correlation is evidence against, not proof of absence. |
| **Clipping or other level-dependent distortion** | Destination-node signals are nominally in `[-1, 1]`; rendition outside that range is undefined ([spec](https://webaudio.github.io/web-audio-api/#audio-values-rendering)). The specification identifies compression as a way to avoid clipping/distorting a simultaneous-sound mix ([spec](https://webaudio.github.io/web-audio-api/#DynamicsCompressorNode)); this graph has the compressor-based limiter above. | Hold scheduling rate and input path constant. Sweep only the app volume and compare a single note, a chord, and repeated overlaps. A repeatable level threshold, with continuous audio and limiter reduction when measured, supports level-dependent distortion. A crackle at very low app level with the same event rate argues against this class. |
| **Late/duplicate app attack** | This app makes a separate `triggerAttack` call per note and routes every input to the shared graph ([attack loop](../../../src/utils/chords.ts#L400-L418)). It also holds a chord receipt so release targets the same engine and notes ([handle contract](../../../src/utils/chords.ts#L304-L338)). | Add temporary *diagnostic-only* timestamps/counters at each input boundary and at `triggerAttackChord`; remove them after the session. One physical tap/key/progression step must produce one chord attack call and its expected note count. Extra calls, or calls arriving after the intended gesture time, identify an event/scheduling problem without assuming an audio-device underrun. |
| **Reverb/sample startup transition** | Reverb IR generation is asynchronous ([Tone source](https://github.com/Tonejs/Tone.js/blob/15.1.22/Tone/effect/Reverb.ts#L91-L125)); the app selects the synth until sampler `onload` sets its state to ready ([app source](../../../src/utils/chords.ts#L245-L263)). | Fresh-reload the app, wait until samples are ready, then compare the first chord with later identical chords. A symptom confined to graph/sample initialization supports this class. A sporadic event after a settled session argues against initialization as the direct trigger. |

## Lifecycle and power: bounded claim

No primary source reviewed establishes POCO M3 power management as the cause, so this note makes no Android-power diagnosis. The Web Audio specification does define `suspended` as context time not proceeding and hardware possibly released, and includes `interrupted` state; it gives phone calls and screen locks as examples where notification can be limited for privacy ([state definitions](https://webaudio.github.io/web-audio-api/#enumdef-audiocontextstate), [interruption algorithm](https://webaudio.github.io/web-audio-api/#interrupting-audiocontext)). The app already releases held chords when the document becomes hidden ([app source](../../../src/utils/chords.ts#L187-L195)).

For a separate foreground/background trial, log `visibilitychange`, `AudioContext.state`, `statechange`, and the audio event timestamps. An artifact preceded by a visibility/state marker belongs in a lifecycle investigation. An artifact while visible with no marker does not support that path. This probe must be run separately from the foreground render-capacity and level sweeps.

## Next probes, in order

1. **Capture one affected session over USB remote debugging.** Record Chrome version, context state, sample rate, callback buffer size, callback interval, and Render Capacity while reproducing the crackle. Keep the phone screen on and disable DevTools screencast while measuring because Chrome warns screencasting reduces frame rate ([Chrome guide](https://developer.chrome.com/docs/devtools/remote-debugging#screencast)).
2. **Run the 2×3 controlled matrix.** For each of one-note, chord, and repeated-overlap cases, test normal and low app volume. Mark whether the sound is continuous/distorted or drops/clicks, then compare against the WebAudio metrics.
3. **Run one startup and one lifecycle control.** Test the first chord after a reload versus a settled session, then perform a hide/lock-and-return trial with the lifecycle markers. Keep these results separate from the foreground matrix.
4. **Only if metrics do not separate the result, count attack calls.** Instrument the input boundaries and `triggerAttackChord` in a disposable diagnostic build. The observed count settles duplicate/late event delivery without changing production behavior.

The clean ordinary-media report is useful context, but it does not by itself distinguish a Web Audio deadline miss, level-dependent distortion, or duplicated app scheduling. No production change follows from this research note.
